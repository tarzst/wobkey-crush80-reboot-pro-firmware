# Периодическое зависание ввода и подсветки

Дата сообщения и уточнений: 2026-10-31.

## Подтверждённое владельцем поведение

- Сбой замечен при переключении эффектов подсветки клавиш, логотипа и боковин
  назначенными на клавиатуре кнопками, без VIA.
- Последующее уточнение владельца: бывает и без переключения эффектов.
  Поэтому RGB не считается обязательным триггером; происходит ли это именно
  при простое либо печати, отдельно не установлено.
- Замирает вся анимация подсветки, клавиатура перестаёт реагировать на ввод.
  Для восстановления владелец выключает питание.
- Наблюдается на USB, BLE и 2.4 ГГц; быстрый перебор не обязателен.
- Переключение режимов подключения работает без зависаний. Первоначальное
  подозрение о транспортном переключении отозвано после уточнения владельца.

Текущая версия по контексту — NativeHeld preview 7d154c51… / CRC350ad5c5;
с устройства при сообщении версия повторно не считывалась. Это аппаратное
наблюдение владельца. Захвата сбоя, точного вызывающего перехода effect ID
и сравнения с stock/RC2 на железе пока нет. USB-enumeration и ответы на
чтение во время зависания неизвестны; полная остановка MCU не доказана.

## Первичный разбор

RGB-коды проходят compact_holds как CCH_STOCK; delta_adapter не меняет
HID-отчёт для таких событий. firmware_binding восстанавливает IRQ-state
перед продолжением штатного dispatch. Застрявший latch сам по себе подавлял
бы отдельную позицию, но не объясняет остановку анимации. Новый путь release
сохраняет исходное назначение после отпускания Fn; его проверяем отдельно.

По последней сохранённой раскладке mode-keycodes — 0x7821 (основной RGB),
0x7f07 (logo), 0x7f0a (side). Это снимок раскладки от 2026-10-21, а не
повторно прочитанные текущие назначения.

Побайтово совпадают в official0108 и NativeHeld:

- основной RGB/custom dispatcher 0xcffc..0xd414;
- logo/side handlers 0x10908..0x10aa4;
- RGB changed helper 0xcd88..0xcff8;
- state-reset helpers 0x95a8..0x95d8;
- таблица custom handlers 0x1be24..0x1be68.

Это не доказывает совпадение всего графа исполнения: вход через matrix изменён,
есть взаимодействие с IRQ, состоянием, отрисовкой и сохранением. Все три mode
пути выставляют gp+805 bit0x20; нужно разобрать его дальнейшую обработку и
сохранение конфигурации. Документированная OEM USB release race пока не
связана с этим симптомом на всех трёх транспортных режимах.

## Ограниченная проверка реальных инструкций

На неизменённых official0108 и опубликованном NativeHeld выполнено по58
сценариев: все19 номеров основного эффекта и по5 номеров logo/side, каждый
с порядком отпускания RGB-key→Fn и Fn→RGB-key. Изменение ожидаемого effect
поля проверяется явно; проходят оба образа. Stack восстанавливается, MIE
остаётся включённым после каждого события.

Это dispatch-only модель: исполняется matrix/dispatch, применена startup RAM,
readiness установлена явно (для NativeHeld вызвана опубликованная C-init),
USB endpoint и busy delays подменены. Нет полного RGB renderer/main loop,
реального radio/Flash и асинхронных IRQ. Отсутствие зависания в этих116
сценариях не означает исправность прошивки и не воспроизводит аппаратный сбой.
Материалы: соседний исследовательский проект Crush, rgb-freeze-20261031/
check_rgb_dispatch.py и dispatch-results.json; в публичный релиз не включены.

Независимое ограниченное ревью подтвердило разделение stock RGB/keyboard
веток и не нашло новой доказанной причины зависания в этом C-пути.

## Первый захват на устройстве — 2026-10-31

По USB подтверждены release 0108, CRC350ad5c5, VIA protocol11 и4 слоя.
Сохранён текущий keymap чтением GET_BUFFER; настроек и прошивки не записывали.
Начальный основной effect ID —18.

Владелец прошёл круг эффектов всех трёх зон без зависания. За295 секунд
получены296 корректных ответов на GET основного эффекта, без ошибок.
Он вернулся к18; опрос раз в секунду мог пропускать промежуточные номера.
Номера эффектов logo/side этим запросом не читаются, их проверка подтверждена
владельцем визуально. Входные HID/input отчёты также записаны.

Сбой не воспроизведён; исправление или причина не установлены. Фоновый GET
может влиять на временные условия. Для следующей попытки опрос остановлен,
запущена отдельная запись только входящих отчётов без команд устройству.
Материалы в исследовательском rgb-freeze-20261031/: initial-rgb.jsonl,
current-keymap.numeric.json, usb-initial.json, live-input-01.jsonl,
live-rgb-01.jsonl и live-trial-01-summary.json.

## Второй захват без опроса

Во второй попытке слушали только входящие отчёты без GET, grab и других
команд устройству. Владелец сообщил об успешных двух кругах каждой зоны.
Записано108 HID-отчётов и108 EV_KEY-событий; запись остановлена штатно.
Отдельного KEY_A в ней нет: запрошенное нажатие A не подтверждено записью.
После остановки снова получены корректные ответы VIA и info: основной
effect18, brightness7, CRC350ad5c5. Это состояние после ручной проверки,
инструменты RGB не меняли. Материалы: live-input-02-no-queries.jsonl,
live-trial-02-summary.json, after-trial-02-rgb.jsonl.

Обе попытки не воспроизвели сбой. Уточнение о зависании вне переключения RGB
расширяет поиск до общего runtime. Зависание в ISR или с выключенными IRQ —
гипотезы, не измеренные состояния MCU. Чтение C-binding и irq_guard.S не
выявило очевидного пропущенного vci_leave на просмотренных путях; это не
доказательство корректности всех IRQ interleavings, стека и OEM callbacks.

## Дизассемблерный и эмуляторный аудит общего runtime — 2026-10-31

Проведён полный разбор таблицы векторов PLIC (`mtvec = 0x8A00`), приоритетов
прерываний (`0xE4000000`), операций с CSR (`mstatus`, `mie`, `0x7D0`, `0x7CA`),
драйвера WS2812 DMA (`0xCB30` / `0x1567C`), обёрток MSPI Flash и маршрутов
сканирования матрицы (`0x30BC` / `0x13D30`):

1. **Обработчик исключений процессора `vec[0]` (`RAM 0x2D6C`, `file 0x2E1C`) и
   невключённый аппаратный Watchdog (`0x80140142`..`0x8014014C`)**:
   - При любом синхронном исключении ядра (`mcause`) процессор попадает в
     `vec[0]` (`RAM 0x2D6C`), который сохраняет `mcause` в `gp+580`, `mepc` в
     `gp+584` и входит в **бесконечный цикл** `0x2E38..0x2E4E` при аппаратно
     сброшенном `mstatus.MIE = 0` (останавливая и сканирование матрицы, и
     анимацию подсветки, пока светодиоды WS2812 продолжают статично светиться
     последним отправленным по DMA кадром).
   - В стоковых `main` (`RAM 0x36D4..0x4048`) и `main_loop` (`RAM 0x4048..0x4254`)
     разработчики WOBKEY вообще не включили Watchdog (`reg_tmr_ctrl2`
     `0x80140142` bit 7 = `0x80`, `reg_wt_target` `0x8014014C`) и не добавили
     его сброс в главный цикл, хотя процедуры сна (`0x0D936`, `0x0EEF4`,
     `0x0F394`) явно выключают бит 7 (`andi a5, a5, 0x7f`), а
     `flash_erase_sector` (`0x8D56`) сбрасывает таймер записью `0x0C` в
     `0x80140143`. Из-за невключённого Watchdog попадание в `vec[0]` или
     зависание с `MIE = 0` не приводило к аппаратному перезапуску МК.
   - **Исправлено в `v1.2.0` (`2026-11-01`, `CRC 13dadb12`)**:
     1) В `cdb_macro_poll` -> `take_macro_request()` при `READY > 7` на каждой
        итерации главного цикла задаётся порог Watchdog `0x8014014C = 0x0B700000`
        (~4.0 с при PCLK 48 МГц), включается бит 7 `0x80140142 = 0x80` и
        сбрасывается счётчик `0x80140143 = 0x0C`. Перед уходом в сон стоковые
        функции `0xD936`/`0xEEF4`/`0xF394` сами отключают бит 7 (`&= 0x7F`).
     2) Полная замена стокового обработчика слоёв `0x12F18..0x130B4` устранила
        заводской конфликт бита `gp+804 & 0x20`, который в стоке выставлялся и
        при нажатии `MO(1)` (`0x12F7C`), и при смене настроек RGB (`0x10908..0x10AC0`),
        ложно запуская фоновую запись/стирание сектора `0x8A000` в `0x1AC64` (`0x1AFC0`).
2. **Приоритеты PLIC и изоляция XIP Flash**:
   - На старте (`0x01F6`) включается `csrsi 0x7d0, 2` (`VEC_PLIC`) и
     `*(0xE4000000) = 3` (preemptive priority + vectored mode).
   - Активные векторы: `vec[1]` (`stimer`, `RAM 0x2C98`, приоритет PLIC **2**),
     `vec[3]` (`timer0`, `RAM 0x2B80`, приоритет PLIC **1**), `vec[15]` (`rf`,
     `RAM 0x27C0`, приоритет PLIC **2**), `vec[23]` (`ws2812_dma_irq`,
     `RAM 0x257C`, приоритет PLIC **1**, сбрасывает флаг занятости DMA
     подсветки `gp+369 = 0`).
   - Во время операций с Flash в RAM (`ILM 0x12CC` и `ILM 0x1524`) порог
     приоритетов PLIC (`0xE4200000`) поднимается до `1` (маскируя `timer0` и
     `ws2812_dma_irq`, но пропуская RAM-обработчики `stimer` и `rf`), а обёртки
     Flash (`0x8C48`, `0x8CE0`, `0x8D44`) временно очищают бит 3 `CSR 0x7D0`
     (`csrci/csrsi 0x7d0, 8`).
3. **Проверка рендерера RGB (`0xA104` / `0xCD88`) в `rc2emu`**:
   - Прогон всех 500 комбинаций режимов `main` (0..19) × `logo` (0..4) × `side`
     (0..4) по 5 кадров (2500 вызовов `0xA104` + `0xCD88`) подтвердил, что все
     6 косвенных переходов внутри `0xA104..0xD000` разрешаются в валидные
     XIP-адреса и возвращают `sp` и `MIE = 1` без ошибок.
4. **Отложенное сохранение (`gp+805` bit `0x20` и `gp+804` bit `0x20`)**:
   - В `0x1AC64` (таймерная служба главного цикла) и `0xEB68` (сохранение
     конфигурации в сектора `0x82000`, `0x83000`, `0x8A000`) запись во Flash
     происходит через штатные обёртки `0xD58C`/`0x8D44` с ожиданием `0xD624`
     (не более `0x1F5` итераций). Вечных циклов ожидания в этих путях нет.
5. **Два маршрута сканирования матрицы (`gp+133`, шорткат `Fn+H` `0x5F8D`)**:
   - При `gp+133 == 0` (значение по умолчанию после холодного старта) функция
     `0x30BC` в `timer0_irq_handler` только выставляет `gp+804 |= 1`, а
     обработка клавиш `0x130B8 -> 0x13268` (`cdb_physical`) вызывается из
     главного цикла (`0x13D30`).
   - При `gp+133 != 0` (низколатентный режим, переключаемый `Fn+H`) функция
     `0x30BC` вызывает `0x130B8 -> 0x13268` (`cdb_physical`) **напрямую из
     прерывания `timer0_irq_handler` (`0x2B80`)**. В `NativeHeld` вызов
     `cdb_physical` защищён `vci_enter/leave` и не вызывает `cdb_oem_send()`
     для обычных клавиш (только для `0x82..0x84` вне критической секции),
     однако в стоковых отправителях (`0x1B624`, `0x10CBC`, `0x125E4`) сброс
     грязных битов `gp+804` выполняется после отправки без запрета прерываний.

## Следующие проверки

1. При следующем зависании сохранить питание и установить, отвечают ли
   VIA/info и приходят ли HID-отчёты; наличие sysfs USB-узла само по себе
   живость контроллера не доказывает. Возможность работы после извлечения
   USB без отключения батареи пока не проверена.
2. Проверить общий runtime: IRQ entry/exit, восстановление MIE, вложенность
   и стек, блокирующие ожидания периферии; затем renderer/callbacks и
   отложенное сохранение. Не ограничиваться обработчиком смены эффекта.
3. Моделировать найденные конкретные interleavings. Установить регрессию
   stock/RC2/NativeHeld по текущим данным невозможно; не менять прошивку
   ради обхода симптома без установленной причины.

Производственные C/ASM, образы и allowlist не менялись. На устройстве
выполнялись только диагностические чтения; эффекты переключал владелец.
Прошивка и автоматическое переключение эффектов не выполнялись.
